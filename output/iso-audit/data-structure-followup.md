# 560.13 XOR structure and signature follow-up

The standard-library script [codex-scripts/iso_data_structure_followup.py](../../codex-scripts/iso_data_structure_followup.py) reconstructs these streams from the extracted ISO data and writes full details to [output/iso-audit/data-structure-followup.json](data-structure-followup.json). It also saves the 4,010,732-byte `560.13 XOR 761.MP3` stream, the 64,167-byte Twitter-XOR prefix, and its base64-decoded PNG under [output/iso-audit/](.). No archive code or ISO executable was run.

The first 64,167 bytes of `560.13 XOR 761.MP3` XORed with reconstructed `twitter.bin` produce the recorded `b64.txt` exactly after removing its CR bytes (the archived text has CRLF line endings while the computed binary stream has LF). That prefix is 20,440 logical Base64 characters plus line breaks, decodes to a 15,330-byte PNG, and matches archived `decoded.png` byte for byte (521 × 523). At offset 20,709, the stream contains a 76-hyphen delimiter line. The following 42,818 logical bytes match archived `only_pattern.txt` after line breaks are removed, and all 42,818 logical pattern bytes follow the `33010` motif with no deviation through offset 64,166 after excluding 563 line-feed wrap bytes.

At offset 64,167 the Twitter data ends. The remaining `560.13 XOR 761.MP3` stream extends 3,946,565 bytes to the 4,010,732-byte audio boundary, but its very first byte (`0x4c`) deviates from every possible phase of the established `33010` cycle. The tail contains no literal `3301` or 16-byte repetition of `3301`. This establishes the exact end of the observed pattern without implying what the following binary stream means.

A bounded scan of `_560.00`, `560.13`, and `560.17` found no PNG or other tested common file/container signature (ZIP, PDF, ELF, XZ, SQLite, 7z, RAR, GIF, or RIFF). The only gzip/bzip-like candidate headers were nine `1f 8b 08` and nine `BZh` occurrences in `560.13`, plus one gzip-like occurrence in `560.17`; none of the gzip candidates decompressed to a valid stream, and none of the bounded common zlib-header candidates validated. All nine `BZh` candidates have an invalid fourth byte (bzip2 requires ASCII 1–9), so none is a valid bzip2 stream header. Decompression checks are capped at 8 MiB output per candidate. These are signature-screen results, not proof against every possible embedded format or custom framing.
