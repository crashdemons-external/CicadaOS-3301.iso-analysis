# 2013 ISO data and XOR static audit

Scope: read-only byte comparisons of the already extracted ISO files and archived source artifacts. No archive scripts or ISO binaries were executed, and no archive content was changed. The reproducible standard-library script is [codex-scripts/iso_data_static.py](../../codex-scripts/iso_data_static.py); machine-readable details are in [output/iso-audit/data-static.json](data-static.json).

## Findings

- The extracted `DATA/560.13` (118,818,811 bytes) matches the full archived counterpart in [archives/archive3/assets/2013/cicados/DATA/560.13](https://github.com/cicada-solvers/documenting-cicada3301-scream314/blob/53e4282d89229b98212ef4f2349310fab6c43532/assets/2013/cicados/DATA/560.13) byte for byte (SHA-256 `db79072c…bc112f`). Several `archive2` copies of `560.13` are only 137-byte Git LFS pointer files, so they are not independent data copies. The extracted `_560.00` and `560.17` match all full copies found across the archives. The extracted `AUDIO/761.MP3` exactly matches the Neuroretransmit archive copy (4,010,732 bytes; SHA-256 `83008217…4ec0a460`).
- The Twitter solve is reproducible from the available documented stream artifacts. XORing the first 4,010,732 bytes of `560.13` with `761.MP3` exactly reproduces archived `560.13^761.mp3.bin`. XORing `twitter.bin` with the MP3, truncating to the shorter input as the archived XOR script does, exactly reproduces archived `gematria.jpg` (64,167 bytes). The README's stream-size distinction matters: the XOR output follows the shorter input, while `560.13` is much larger.
- The first-onion `clue.txt.bin` XOR `_560.00` reproduces the archived signed message byte for byte after normalizing CRLF to LF. The third-onion documented ciphertext at offset 12,821 XORs to `gbyh7znm6c7ezsmr.onion\n`; the derived 23-byte stream is saved as [output/iso-audit/third-onion-offset-12821.bin](third-onion-offset-12821.bin).
- ISO `/tmp/folly` and `/tmp/wisdom` are identical 3,368-byte streams, SHA-256 `7e5ec097…31c385a`; every archived full copy found is likewise identical. Their bytes span all 256 byte values and do not read as plaintext. This establishes duplication, but the available evidence does not explain whether the names indicate a deliberate decoy, shared encrypted payload, or some other design. The pairwise XOR is all zeros by consequence of identity, so it does not reveal further structure.
- `.rev` files are not uniformly reverse-byte copies. Across the discovered `.rev`/candidate pairs, 47 of 57 pairings were literal reversals; the remainder include differing lengths and duplicate-corpus pairings. These counts are pairwise, not counts of unique assets. Per-pair outcomes are recorded in the JSON.

## Historical linkage and caveats

The Twitter README documents the 560.13/761.mp3 and Twitter stream chain; the first-onion README documents `clue` XOR `_560.00`; and the third-onion README documents offset-based XOR over `560.13`. The archive3 2013 chronology independently describes the historical 761/Twitter XOR and 560.13-based extraction. These are later/community records, while the exact matches above establish that the recorded artifacts and extracted bytes are internally consistent. The ISO's provenance/authenticity remains separate from these byte comparisons.
